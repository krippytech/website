External Repair Required a Data-Custody Plan

A device needed to leave organizational control for hardware repair. The technical job was not only to ship the endpoint.Cloud access, local cached data, continuity, and the post-repair rebuild all had to be controlled.

Investigation

How was the custody change handled?

External repair is a custody change. Protect the data before the hardware leaves organizational control.

Removing an application is not proof that synchronized business data is gone.

Investigation path: Repair decision → Continuity check → Stop sync → Unlink cloud relationships → Remove local cached data → Verify absence → Transfer custody → Factory-reset return → Known-good rebuild → Reconnect required libraries

Finding

What was actually proven?

The repair workflow had to include data protection

Before shipment, active OneDrive and SharePoint relationships were disconnected, local synced content was removed as intended, and a separate endpoint preserved business access. After the repaired device returned in a factory-reset state, required applications and cloud libraries were re-established.

The case does not claim one universal depot procedure, that uninstalling a sync client always removes all local data, or that every repair requires the same continuity method.

Verification boundary

Confirm alternate access first, stop and unlink sync relationships, verify the sync client is no longer active, verify locally cached data is removed as intended, and reconnect only the required libraries after the endpoint returns and is rebuilt.
